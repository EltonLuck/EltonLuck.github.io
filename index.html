Current build · Main project

URL Shortener

A URL shortener I'm building now in Java 21 and Spring Boot. It turns long links into short base62 codes derived from database-generated IDs, stores them in PostgreSQL, and resolves them through a Redis cache. It's in active development — what's built and what's still planned are listed separately below.

In progress
Java 21Spring BootREST APIsPostgreSQLRedisDocker Compose
// create
POST /api/links → 201 + base62 code from the row ID

// resolve — cache-aside
GET /{code} → Redis hit? 302 : Postgres → cache → 302 · unknown code → 404

Implemented

  • Link creation — POST /api/links validates the URL, persists it in PostgreSQL, and returns a base62 short code encoded from the database-generated row ID.
  • Redirects — GET /{code} returns a 302 through a Redis cache-aside lookup, with a clean 404 for unknown codes.
  • Rate limiting — POST /api/links is limited to 10 requests per minute per IP with Bucket4j; further requests return a 429 with the wait time.
  • Local stack — Postgres 16 and Redis 7 run via Docker Compose, with the app health-checked against both.
  • Tests & CI — Testcontainers integration tests run against real Postgres 16 and Redis 7, alongside unit tests for rate limiting and base62 encoding; the 7-test suite is green locally and in GitHub Actions CI.

In progress & planned

  • Load testing and deployment — planned; no benchmarks or live demo yet.
View the code on GitHub ›
  • Short codes are base62 encodings of the row ID, so a code can never collide with another link — no random generation or retry loop.
  • Redirects are the hot path: they check Redis first and only fall back to Postgres on a miss, then cache the result.
  • The codebase is organized package-by-layer — controller, service, repository, entity, util — with design decisions recorded in the repo as the build progresses.

Working style

How I work

I learn by taking a real system apart, rebuilding the important path, and proving it with tests—not by collecting disconnected tutorials.

01Model the failure first.

Retries, duplicate requests, bad inputs, and interrupted flows shape the design before the happy path does.

02Make boundaries obvious.

Authorization belongs at the edge. Business rules belong on the server. Secrets never belong in the client.

03Ship proof, not promises.

Smoke tests, explicit states, and reproducible setup turn “it works” into something another engineer can verify.
